# 11 - 原生重写可行性评估（Flutter → ArkTS UI + C++ 内核）

> 状态：评估结论，未启动实施
> 日期：2026-10-22
> 分支：feature/harmony
> 关联：[01-可行性分析](01-可行性分析.md)、[09-应用白名单与VPN路线实施](09-应用白名单与VPN路线实施.md)

## 1. 背景

当前鸿蒙版是 Flutter 应用：`ohos/entry/src/main/ets/pages/Index.ets` 只挂载 `FlutterPage`，UI 与代理内核全部运行在 Dart，ArkTS/C++ 仅承担 VPN 隧道、后台保活、画中画等平台能力。

本文评估一个问题：**能否把鸿蒙端全部改用鸿蒙原生语言（ArkTS）实现？**

## 2. 结论摘要

1. **纯 ArkTS 重写不可行。** ArkTS 的证书 API 只能解析/校验 X.509，不能创建、签发、自签名；TLS 服务端证书只能在 `listen()` 时静态传入，没有按 SNI 动态换证书的接口。因此 HTTPS MITM 所需的动态证书链必须依赖 C/C++（NDK + OpenSSL/BoringSSL）。brotli/zstd 解压与 JS 脚本引擎同样没有纯 ArkTS 路径。
2. **ArkTS UI + C++/NDK 内核技术上可行**，属于 **XL 级重写**：约 1.8 万行 Dart 代理内核和约 2.8 万行移动端 UI 需要重写。目前未发现可参考的成熟"纯 ArkTS MITM 代理"开源实现。
3. **当前不建议启动全量重写。** 现有 Flutter 版本已通过路线 A（VPN 抓包）与路线 B（局域网代理）真机验收；重写的主要收益是移除 Flutter 引擎与工具链补丁，代价是失去 Android/桌面共享内核，并引入长期双栈维护。建议仅在出现明确触发条件（见 §9）时启动。

## 4. ArkTS 能力边界（官方结论）

| 能力 | ArkTS 现状 | 结论 |
|---|---|---|
| TCP Server / 自定义 DNS / CONNECT 透传 | 支持（`@ohos.net.socket` TCPSocketServer 等） | 可做 |
| TLS 服务端 | 支持，但证书只能 `listen()` 时静态传入 | 不足以支撑 MITM |
| 按 ClientHello SNI 动态换证书 | **不支持** | 必须 NDK |
| X.509 创建 / 签发 / 自签名 | **不支持**，`@ohos.security.cert` 仅解析/校验 | 必须 NDK OpenSSL/BoringSSL |
| HTTP/1.1 服务端 | 无官方库 | 基于 TCP 自实现 |
| WebSocket 服务端 | API 19+ 提供 `createWebSocketServer` | 当前 API 24 可用 |
| brotli / zstd | 无系统 API（`@ohos.zlib` 仅 zip） | 必须 NDK 或三方库 |
| JS 脚本 | ArkTS 禁用 `eval`/`new Function` | JSVM-API 或 NDK QuickJS |
| 已安装应用枚举 | 三方应用不可用（仅 PC/2in1 或企业权限） | **换语言不解决** |
| 程序化安装 CA / 系统代理 | 不支持 | **换语言不解决** |

官方依据：
- [@ohos.net.socket（TCP/TLS socket）](https://developer.huawei.com/consumer/cn/doc/harmonyOS-references/js-apis-socket)
- [证书对象的创建、解析和校验](https://developer.huawei.com/consumer/cn/doc/harmonyOS-guides/create-parse-verify-cert-object)
- [@ohos.net.webSocket](https://developer.huawei.com/consumer/en/doc/harmonyos-references/js-apis-websocket)
- [@ohos.zlib](https://developer.huawei.com/consumer/cn/doc/harmonyOS-references/js-apis-zlib)

> 平台硬限制（应用枚举、CA 安装、系统代理、证书固定、后台保活）与本议题无关，重写不会改善，相关结论仍以 [07](07-风险登记册.md)、[09](09-应用白名单与VPN路线实施.md) 为准。

## 5. 路线对比

| 路线 | 做法 | 评价 |
|---|---|---|
| C. 整体重写 | 一次性替换 UI + 内核 | 回归面不可控，否决 |
| A. 独立原生工程并存 | 新建 native 工程，Flutter 版冻结 | 风险隔离最好，但两套产品长期双维护，总成本最高 |
| **B. C++ 内核先行** | 先实现 C++ 内核 + NAPI，Flutter 经插件继续当壳；再逐步替换 ArkTS UI | **推荐（若启动）** |

路线 B 的关键约束：

- Flutter 由 `FlutterAbility` 承载，**无法嵌入 ArkTS 同一导航栈**；两套 UI 只能以两个 Ability / 两个 product 共存，按入口切换。
- 过渡期 `lib/`、`android/`、`ios/`、桌面工程保持不动，继续满足"五平台可构建"约束（见记忆/项目约定及 [05](05-平台分支改造方案.md)）。
- Dart 内核保留为协议 oracle，用于同流量回放对比。

## 6. 分阶段方案（若启动）

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| **P0 POC（S）** | ArkTS 测试页 + C++ demo | ① NDK OpenSSL 按 ClientHello SNI 动态签发叶证书，TLS 1.3 / ALPN 握手通过；② NAPI `napi_threadsafe_function` + ArrayBuffer 大 body 吞吐达标；③ QuickJS 或 JSVM 承接现有脚本 API；④ Dart → MethodChannel → ArkTS → NAPI 链路稳定。任一不满足即停止 |
| **P1 内核 + Flutter 壳（L）** | HTTP/1.1、CONNECT、SOCKS5、MITM/证书、流存储、基础重写、NAPI | 与 Dart 内核同流量回放对比，关键响应一致 |
| **P2 协议完备 + ArkTS UI（L）** | H2/HPACK/WS、断点/限速/脚本/压缩；首页、列表/详情、设置、工具箱 | native 与 Flutter product 并存，功能矩阵对齐 |
| **P3 对齐切换（M）** | 长稳、大流量、发热、VPN/PiP/后台回归 | 切换默认入口，冻结 Flutter ohos 路径 |

### 6.1 直接复用

- `tunnel.cpp` / `packet.cpp` / `session.h` / `port_map`：tun fd → 127.0.0.1:9099 语义不变。
- `ProxyPinVpnAbility`、PiP / KeepAlive / Share / Scan / ProcessInfo 插件。
- `module.json5` 的权限、`backgroundModes`、VPN extension 声明。

### 6.2 C++ / ArkTS 职责边界

| C++（NDK） | ArkTS |
|---|---|
| 监听、HTTP/1.1、HTTP/2、WebSocket、SOCKS5 | UI、Ability 生命周期 |
| TLS MITM + 动态 X.509 签发 | VPN 配置 / protectProcessNet |
| brotli / zstd 压缩 | relationalStore 持久化 |
| 重写 / 断点 / 限速 / 访问控制 | 设置与规则编辑 |
| 流与 body 存储、QuickJS | 证书导出与安装引导、导入导出 |
| 隧道入口 | PiP、保活、扫码、分享、l10n |

NAPI 原则：热路径全在 C++；桥接只走控制面 + 批量事件，禁止逐包/逐 chunk 过桥；body 按需拉取（`getFlow` / `getBody(id, side, offset, len) → ArrayBuffer`）；独立 IO 线程 + 背压。可沿用现有 `startTunnel` / `stopTunnel` / `isTunnelRunning` / `getRemoteByPort` 接口风格。

## 7. 主要风险（按严重度）

| # | 风险 | 等级 |
|---|---|---|
| 1 | TLS MITM 兼容性（TLS 1.3 / ALPN / 证书固定） | 高 |
| 2 | ArkTS UI 重写量（40+ 页面/组件） | 高 |
| 3 | H2 / HPACK / WebSocket / 重写语义对齐 | 高 |
| 4 | NAPI 性能、线程安全、大包 | 中高 |
| 5 | QuickJS 脚本 API 兼容 | 中 |
| 6 | 双栈漂移与五平台 CI | 中 |
| 7 | 内核驻留进程（主进程 vs `:vpn` 扩展进程） | 中 |

## 9. 决策门槛

**放弃 / 回退门槛：**

- P0：主流 50 应用 MITM 成功率 < 90%，或吞吐 < Dart 版 70% → 停止。
- P1：回放一致率 < 95%，或连续两阶段未过验收 → 回退 Flutter。
- 五平台构建被破坏超过一个发布周期 → 冻结重写。

**启动触发条件（满足其一再评估）：**

1. 鸿蒙商店或合规明确拒绝 Flutter 应用；
2. Flutter-ohos 引擎/工具链无法继续维护（如 SDK 升级持续受阻）；
3. 性能、包体或系统集成成为硬性指标。

否则，继续维护 Flutter 版本是成本更优的选择。
